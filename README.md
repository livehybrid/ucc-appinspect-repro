# ucc-gen output fails AppInspect 4.3.0 out of the box

A minimal reproduction: **everything in this repo is `ucc-gen init` output.** No
hand-written app code, no custom templates, no extra dependencies. Build it with the
latest `ucc-gen` and scan it with the latest AppInspect, and you get one failure and
three future-failures — all in files `ucc-gen` generates.

## Versions

| Component | Version |
| --- | --- |
| `splunk-add-on-ucc-framework` | 6.5.3 (latest, 2026-07) |
| `splunk-appinspect` | 4.3.0 (latest, released 2026-07-29) |

## Reproduce

```bash
pip install --upgrade splunk-add-on-ucc-framework splunk-appinspect
ucc-gen build --source package -o output --ta-version 1.0.0
tar czf app.tar.gz -C output TA_ucc_mako_repro
splunk-appinspect inspect app.tar.gz --mode precert --data-format json \
  --output-file report.json --max-messages all
```

This repo was generated with:

```bash
ucc-gen init \
  --addon-name TA_ucc_mako_repro \
  --addon-rest-root ta_ucc_mako_repro \
  --addon-display-name "UCC Mako Repro" \
  --addon-input-name example_input \
  --addon-version 1.0.0 \
  --add-license "Apache License 2.0"
```

Only `globalConfig.json` and `package/` are committed — `output/` is a build artifact.

## Results

`{"error": 0, "failure": 1, "future_failure": 3, "not_applicable": 114, "warning": 14, "success": 120}`

### 1. `check_for_custom_mako_templates` — future failure

> Custom Mako template file `appserver/templates/base.html` is deprecated in Splunk
> Enterprise 10.4. Future Splunk platform versions will no longer support custom Mako
> templates. Remove the custom template. For UCC-generated apps, regenerate the app with
> UCC framework version '6.3.0' or later.

The remediation cannot be followed. That file is copied verbatim from
`splunk_add_on_ucc_framework/package/appserver/templates/base.html`, i.e. ucc-gen ships
it. This build used **6.5.3**, well past the suggested 6.3.0, and it is still emitted.
An add-on author has no supported way to remove it — deleting it post-build risks the
UCC configuration page, which renders through it.

This check is **new in AppInspect 4.3.0**; it does not exist in 4.2.1, so this finding
appears the moment you upgrade.

### 2. `check_modular_inputs_python_required` — future failure

> Stanza `[example_input]` does not define `python.required`.

`default/inputs.conf` is generated by ucc-gen from `globalConfig.json`. Hand-editing it
is futile — the next build overwrites it.

### 3. `check_admin_external_restmap_conf_python_required` — future failure

> Stanza `[admin_external:ta_ucc_mako_repro_account]` does not define `python.required`.
> Stanza `[admin_external:ta_ucc_mako_repro_settings]` does not define `python.required`.

`default/restmap.conf` is likewise generated by ucc-gen.

### 4. `check_aarch64_compatibility` — failure

> Found AArch64-incompatible binary file: `lib/google/_upb/_message.abi3.so`
> Found AArch64-incompatible binary file: `lib/grpc/_cython/cygrpc.cpython-312-x86_64-linux-gnu.so`

These come from the stock `package/lib/requirements.txt` that `ucc-gen init` writes
(`splunktaucclib`, `splunk-sdk`, `solnlib`) and their transitive dependencies. A default
add-on therefore ships x86_64-only binaries.

## Why this matters

Findings 1-3 are future-dated today, so they do not block packaging yet. When those
deadlines pass they become hard failures, and at that point **every UCC-generated add-on
fails AppInspect until ucc-gen changes** — the app author cannot fix generated files.

AppInspect 4.3.0 has already done exactly this to twelve other checks: they were
future-failures in 4.2.1 (tagged `Tags.FUTURE`, emitting a warning plus
`FailMessage(release_version=4.3.0)`) and are now unconditional failures. Eleven of them
are `tools.conf` rules. The same escalation is the expected path for these three.

## A second finding: the shared CI pipeline cannot see any of this

The first CI run of this repo passed — including the `future` tag group. That is not
because the findings are absent; it is because
[`livehybrid/appinspect-cli-action`](https://github.com/livehybrid/appinspect-cli-action)
pins its scanner in `requirements.txt`:

```
splunk-appinspect==4.2.1
```

AppInspect 4.2.1 does not contain `check_for_custom_mako_templates` — the check did not
exist until 4.3.0 — so the pipeline cannot report it. Every repository using that shared
action is being vetted against a scanner that is releases behind, and will keep passing
until the pin moves.

The workflow in this repo therefore runs AppInspect **twice**, and the contrast is the
point:

| Job | Scanner | Result |
| --- | --- | --- |
| `appinspect-latest` | latest, installed directly | **fails** on the future-failures above |
| `appinspect-shared-pipeline` | shared action, pinned 4.2.1 | passes, masking them |

## What this repo does

It builds with the **latest, unpinned** ucc-gen, then asserts directly that ucc-gen
emitted `appserver/templates/base.html` and left `python.required` out of the generated
conf files — so the findings cannot be attributed to anything in this repository — and
finally runs the two AppInspect scans above.

It re-runs weekly, so if either toolchain fixes this the build goes green on its own.
